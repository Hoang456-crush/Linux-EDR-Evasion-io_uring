SLIDE 3 — The Problem

⏱️ 1 minute 30 seconds ⭐⭐⭐ KEY SLIDE

═══════════════════════════════════════════

🎤 SAY:

"Every major Linux EDR — Elastic Defend, CrowdStrike Falcon, SentinelOne — depends on eBPF probes attached to the kernel syscall table.

The critical assumption is: every useful I/O operation must pass through the syscall dispatch table.

io_uring, introduced in Linux 5.1 in 2019, invalidates this assumption.

io_uring uses kernel worker threads called io-wq to perform I/O operations. These threads bypass the syscall table entirely. File reads, network connections, file deletions — all happen with ZERO events in strace, auditd, Falco, or any eBPF-based monitoring tool.

This isn't theoretical. Google banned io_uring on Android and ChromeOS because 60% of kernel vulnerability submissions involved io_uring. And in 2025, RingReaper became the first real-world malware weaponising io_uring for EDR evasion.

The question is: can we exploit this blind spot, and more importantly, can we detect it?"

SLIDE 6 — How Linux EDRs Work (Part 2 — io_uring bypass)

⏱️ 1 minute ⭐⭐⭐ KEY SLIDE

═══════════════════════════════════════════

🎤 SAY:

"This diagram shows the io_uring architecture. Instead of making individual syscalls, the application places I/O requests into a Submission Queue — a shared ring buffer.

The kernel picks these up using its own worker threads, called io-wq, executes the operations, and places results into the Completion Queue.

The critical point is: these kernel worker threads never pass through the syscall dispatch table. The eBPF hooks that EDRs rely on are attached to the syscall table — so they see nothing.

Only two syscalls are visible: io_uring_setup — to initialise the ring buffer — and io_uring_enter — to submit batches. But the actual file reads, network connections, and deletions are completely invisible.

I call this the EDR Blind Zone."

SLIDE 7 — LD_PRELOAD (Part 1)

⏱️ 1 minute

═══════════════════════════════════════════

🎤 SAY:

"LD_PRELOAD is the second layer of our evasion framework.

It instructs the dynamic linker to load a malicious shared library before libc, allowing us to override standard glibc functions.

Here's how it works: When an administrator runs ls /tmp/, the dynamic linker loads our evasion_hooks.so first. Our hooked readdir() function filters out malicious filenames — like evil.so and evasion_ops — then calls the real readdir() underneath.

The result: the administrator sees a clean directory listing. The malicious files are invisible.

We hook 13 glibc functions — covering ls, find, stat, cat, test, Python's os.path — essentially every tool an administrator might use to inspect the filesystem."

SLIDE 17 — Phase 3 REAPER Differential

"This slide presents one of the central findings of this thesis.

Phase 3 has three sub-phases, and they have dramatically different detection outcomes based on their implementation purity.

Phase 3c — Kill EDR Process: The kill() syscall is visible, but our Rule 7 queries logs-endpoint.* — which is empty because Elastic Defend doesn't log its own termination. So it's visible but not detected.

The key insight: implementation purity determines evasion success. Pure io_uring is invisible. Mixed implementations leak."

SLIDE 18 — ACTION vs EFFECT

⏱️ 1 minute ⭐⭐⭐ KEY SLIDE

═══════════════════════════════════════════

🎤 SAY:

"This is the central theoretical contribution of this thesis.

io_uring hides the ACTION — the syscall execution — but it cannot hide the EFFECT — the filesystem changes and process state modifications.

Let me walk through the table:

Phase 1, io_uring_setup: The ACTION is always visible — this is a mandatory syscall that cannot be bypassed. This is our universal chokepoint.

Phase 2, C2 network: Both ACTION and EFFECT are invisible — complete evasion.

Phase 3b, BPF maps: The ACTION is partially visible due to the opendir() leak, and the EFFECT is detected by FIM on bpffs.

Phase 5, ld.so.preload: The ACTION — writing the file — is invisible via io_uring. But the EFFECT — the file now exists on disk — is detectable through File Integrity Monitoring and process environment analysis.

This framework explains why some phases are detectable and others are not, and it guides where defenders should focus: monitor EFFECTS, not just ACTIONS."

🎯 Q&A PREPARATION — Top 10 Expected Questions

═══════════════════════════════════════════

Q1: "Why didn't you test against CrowdStrike or SentinelOne?"

ANSWER: "This is acknowledged as a limitation. We focused on Elastic Defend because it's open-source with full eBPF visibility, which enabled us to analyse exactly what telemetry was and wasn't captured. However, all three EDRs share the same fundamental architecture — eBPF hooks on the syscall table — so our findings regarding io_uring evasion should generalise. Cross-platform testing is proposed as future work."

Q2: "Why is Phase 3b detectable but 3a isn't?"

ANSWER: "This is our central finding. Phase 3a uses pure io_uring — every operation goes through the ring buffer, generating zero traditional syscalls. Phase 3b must enumerate a directory, which requires getdents64 — an operation io_uring does not support. So the code falls back to opendir() and readdir(), which are traditional syscalls visible to Auditbeat. This syscall leak, combined with FIM events on bpffs, triggers 28 alerts. The root cause is an io_uring API limitation."

Q3: "How practical is this attack in the real world?"

ANSWER: "RingReaper, discovered in 2025, proves this is not theoretical. It uses io_uring for credential collection, network C2, and file reconnaissance — exactly the same operations in our Phases 2 and 4. Our toolkit demonstrates the full attack chain is feasible with approximately 1,200 lines of C, requiring only a standard Linux kernel 5.1 or later. The io_uring API is available on every modern Linux distribution."

Q4: "Why only 83% TPR? What about the remaining 17%?"

ANSWER: "The 17% gap represents operations that produce no detectable EFFECT — specifically, credential file reads and network C2 operations through io_uring. These operations don't modify the filesystem, so FIM cannot detect them. The reads also don't trigger auditbeat events because auditbeat monitors syscalls, not io_uring ring buffer operations. Closing this gap requires kernel-level instrumentation of io_uring completion paths, which we propose as future work."

Q5: "What's the difference between ACTION and EFFECT?"

ANSWER: "ACTION is the syscall execution itself — the openat(), read(), write() call. This is what EDRs monitor. EFFECT is the result — the file that now exists on disk, the process state that changed, the network connection that was established. io_uring hides the ACTION by using kernel worker threads instead of the syscall dispatch path. But it cannot hide the EFFECT — if you write to /etc/ld.so.preload, that file now exists and is detectable by FIM regardless of how it was written."

Q6: "Could io_uring be disabled entirely?"

ANSWER: "Yes — and some organisations do this. Docker removed io_uring from its default seccomp profile, and Google banned it on Android. However, io_uring provides significant performance benefits for legitimate applications — database engines, web servers, high-frequency I/O. Disabling it entirely creates a functionality trade-off. Our approach of monitoring io_uring_setup as a chokepoint is a more balanced solution."

Q7: "How does LD_PRELOAD persist across reboots?"

ANSWER: "Through /etc/ld.so.preload. When a line is added to this file pointing to our shared library, the dynamic linker automatically loads it for every new process on the system — including after reboot. Unlike LD_PRELOAD environment variable, which only affects the current process tree, ld.so.preload is system-wide and persistent. This is why FIM on /etc/ld.so.preload is critical for detection."

Q8: "What happens when the EDR auto-restarts after being killed?"

ANSWER: "Elastic Defend is managed by systemd and auto-restarts within seconds. However, during the window between kill and restart, the attacker can perform operations with zero monitoring. In our testing, this window was approximately 3-5 seconds — sufficient for credential exfiltration. After restart, the EDR resumes normal monitoring, but it has no record of what happened during the blind window."

Q9: "Why did you use Auditbeat instead of just Elastic Defend?"

ANSWER: "Elastic Defend's eBPF probes monitor the syscall dispatch path — which io_uring bypasses entirely. We needed Auditbeat because it provides kernel-level audit rules that can capture io_uring_setup and io_uring_enter syscalls directly, plus File Integrity Monitoring on critical paths. The combination of both gives us the multi-layer detection capability that neither provides alone."

Q10: "What ethical considerations did you address?"

ANSWER: "All testing was conducted in an isolated laboratory environment with no connection to production systems. The toolkit was designed for educational and defensive purposes — enabling security teams to understand and prepare for io_uring-based threats. We followed responsible disclosure principles, and our detection framework ensures that the defensive contribution outweighs any potential offensive misuse. The research was approved by the university ethics committee."
